# Mechanics 建模

机制建模帮助读者沿规则理解相关概念与系统如何相互影响，不是罗列名词、复刻操作流程或仅让节点连通。建设基础玩法模型时，也应为后续物品提供可复用的作用对象；分类图、孤立身份录入和局部修改不因此承担完整玩法建模任务。

- **设计建模**以作者声明的玩法关系为依据；数值、公式或实现未定，不妨碍表达已确定的影响方向、收益与代价。概率倾向也是设计关系，不代表每次必然发生。
- **还原既有玩法**时核实相应来源，不把设计提案写成现状。真正互斥而未决定的玩法选择保留待定，但不以此省略其他已确定关系。

只运行 `node <项目>/.mechanics/tools/workspace-tool.mjs`。工具直接读写项目 JSON，不依赖 CLI、网页或 HTTP；DSH 检索/图卡插件不提供写入能力。使用与本 skill 配套的工具合同（`contractVersion >= 8`，打开草稿时返回）；旧工具不具备完整保存门禁，应同步受管工具，不能用人工检查代替。

## 默认流程：打开 → 编辑 → 保存

1. **打开草稿**：目标已知时直接 `draft open --mechanic <机制ID>`，使用返回的草稿 ID 与路径，不必先跑 `guide`、`scopes` 或查询。新建时加 `--name <名称> --scope <范围>`，可加 `--folder <已有目录>`；已有可继续使用的草稿不重复打开。
2. **编辑相关内容**：只按任务和编辑工具需要，定向读取、修改返回的 `definitions.json`、`rules.json`、`mechanic.json` 中相关部分。它们包含全库定义/规则和当前图；保留无关条目，不要求三份逐一通读、全量人工比对，也不要自行编写预检脚本。字段不确定才查 `guide` 的模板。只改草稿，不直接写 canonical，不填写几何缓存。
3. **直接保存**：`draft save --draft <draftId>`。save 自行检查格式、版本、ID、全工作区引用、概念锁、基线冲突和保存结果；失败时给出诊断。**不需要先调用 `draft validate`，不需要另一次审批或成功后固定重查。** `saved: true` 即本次保存完成，按返回结果简要交付。

脚本负责可机械判定的结构、引用与写入安全；建模师负责规则含义、来源性质、颗粒度及本次任务范围的关系覆盖。`saved: true` 表示保存完成，不替代语义目标完成。围绕本次目标判断关键输入、输出、状态/资源、代价或反向通道及跨边界远端影响是否表达清楚，不另加审批、预检脚本或全库复读，也不要把脚本校验职责变成 Agent 的人工核对清单。

## 仅在需要时使用

| 情况 | 操作 |
| --- | --- |
| 字段合同未知、版本变化或字段报错 | `guide`：查本次需要的模板/约束；不要求每次编辑重读 |
| 目标机制或已有目录未知 | `scopes`：定位目标；基线由 open/save 管理，不手抄 revision |
| 概念身份或现状规则来源不明 | 选择合适的 `search`、`node` 或 `impact`；不是全部依次调用。模糊候选仍须用稳定 ID 消歧 |
| 只想检查、不想提交 | `draft validate --draft <draftId>`：同一保存前检查的 dry-run，不发校验凭据，也不是 save 的前置条件 |
| 保存报错 | 按错误中的路径、字段、ID 定向检查和修复；修好后直接 save |
| 用户要求展示、分析或保存结果不确定 | 仅对相关目标查询/读取，不把全库复读设为常规结尾 |

- 格式/引用/锁等预检失败不写 canonical，草稿保留；冲突后重新打开最新基线，仅重新应用本次意图，不强行重放旧全库副本。
- 脚本不会替你解除其他图或视图的引用。只有报错指出跨文件依赖、且任务确需清理它们时，才处理相应消费者；超出单图草稿能力则交接，不先保存已知断引用状态。
- 写入故障区分「已回滚」「回滚不完整/结果不确定」与「已保存但清理有警告」。按实际结果处理，不能把已提交后的清理警告当作未保存而重试整次修改，也不能对回滚失败声称零写入。
- 多张图仍顺序打开、保存，再开下一张，避免全库草稿基线互相过期。无需为普通新增或文字修改制作额外分类表、比对报告或请求重复批准。

## 概念身份与压缩

概念压缩先判断**是否同一身份**，而不是先删节点。新建基础模型或大范围重整时，按以下顺序收敛候选；普通局部修改只处理本次触及的概念，不强制全库重审：

1. **同一语义 → 复用/alias**：两个名称指向同一稳定对象或度量，并且在相关规则中不存在“一者改变、另一者不变”的合理状态时，复用一个概念；旧名、跨语言名写入 `aliases`。先按稳定 ID、完整名称和完整别名精确解析，不能按相似名称自动选择 canonical。
2. **单条规则的参与者子集 → qualifier**：差异只缩小某条 influence 的角色、阵营、对象或阶段范围时，写端点限定词；限定词不创建身份，也不适用于结构关系。
3. **真正的种类关系 → is-a**：任一子概念实例都能无条件称为父概念，且两者属于同一语义维度时，才声明 `specializes`。每个概念只有一个稳定主身份父类；稀有度、来源、玩法职责等正交分类使用 tags。is-a 是分类，不是 OO 式效果继承。
4. **稳定组成关系 → part-of**：局部是跨机制仍成立、可命名的整体组成时，声明 `part-of`（局部 → 整体）。允许一个局部属于多个整体，但禁止自连与环；它不表示影响、继承或传递组成。动态库存成员、临时持有、位置、所有权、目录收录和流程步骤都不是 part-of。
5. **真实变化关系 → influence**：一者的增加、发生或存在确实使另一者改变时，分别保留概念并声明影响；“金币余额”和“购买能力”相关但不是同一概念，“左臂生命”影响“角色生命”也不能用 tag 或 part-of 代替影响。
6. **纯阅读组织 → tag/scope/目录/视图**：局部—整体只表示页面范围、分析尺度或人工分类时，用这些元数据，不创建概念和语义边。tags、label、目录和 scope 都不参与结构、继承或推理。

可独立变化、生命周期、参与者或结算边界不同的候选，即使连接结构相似，也不得合并。视觉折叠、限定投影、is-a 与 part-of 都不等于 canonical merge。疑似重复概念需要合并时，不使用自动 merge：先分别精确解析稳定 ID，用 `node` 查看直接声明，再以双向 `impact` 核对双方与关键邻接概念的影响路径；随后逐项修改定义、规则文字与端点、固定引用和焦点。合并可能改变规则含义，不能只搬连线，也不能把 save 成功当作语义合并正确。

反例：怒气和法力都具有产生/消耗结构，但可独立变化，不能合并为“能量”；手牌与手牌数量不是同一概念或 is-a；左臂 part-of 角色，绝不是 is-a 角色；火焰伤害 is-a 伤害则成立。

## 先识别影响，再选择概念

- **一条作者声明的 `influence` 边就是一个原子影响规则**：源概念沿定义方向变化时，目标概念受到有向正向、负向或随机影响。机制图围绕 `scope` 选择共享规则与概念，用来观察抽象关系，不是还原一次执行的先后流程；图也可以包含非影响的 `specializes` 分类边、`part-of` 组成边或没有连线的焦点概念。不要为凑成连通路径虚构影响。解释机制整体或系统关联时，应能沿所选有向规则读出本次范围的主要收益、代价、资源转化与反馈；不能以允许孤立或避免流程图为由省略已确定关系。连通性本身不证明方向、条件与含义正确。
- 先问「哪两个稳定概念之间存在什么影响」，再决定端点；不要先把“拥有→激活→检查条件→执行→产出”逐步建成节点再补箭头。概念的 `description` 只定义它是什么、指向什么对象，不承载该条规则的触发、时机、数值和例外；这些写在相应边的 `ruleText`，边的方向与 `sign` 仍须和文字一致。同一有向端点对的多个条件合入同一条规则文字，不按条件各造一条边；文字条件不会被图路径自动求值。
- 普通中间概念只有在它本身可独立定义，且作为其他影响的输入、输出、共享事件/资源、反馈状态或本图明确要分析的对象时，才值得单独建模；只为转述执行顺序或包装一次条件判断而存在的单链步骤，通常内联到规则文字。不要仅凭当前图单入单出就删除：先看全局复用与语义边界；具体物品身份、合理终点和孤立焦点也不受此内联判断约束。购买、安装、结算等承担资源转换或配置改变的事件，不因存在先后时序就属于冗余流程节点。折叠只改显示，不等于删除规则或概念。
- 创建或重整供后续物品复用的基础机制时，辨明可分别改变的量、资源、状态与共享事件，不强求统一数值化，不混淆类别、持有实例、装备状态与数量。可用少量不同方向、不同代价的假想效果试写，例如数量更多但单价更低、容量更大但作用频率更慢，检查能否用已有作用对象清楚表达；示例不作为物品定案。在既定玩法内复用这些概念，不为每个物品临时发明业务概念；真正引入新玩法时再扩展模型，不预建万能概念或为每种状态复制整套指标。检查范围由任务目标决定，局部修改不强制做整套效果试写。
- **条件不是促进边**：例如“当前没有护盾才补盾”，不等于“护盾增加会促进补盾物品”；优先写在物品→护盾的规则文字里，不造条件读取→物品的伪影响。反过来，若“施放中”真实抑制再次使用，状态→使用是独立影响，应保留。资源可用量若真实改变行动机会，也应保留影响：金币支持可成交购买，实际购买又消耗金币；两条边可同时成立，不代表金币自动触发购买。阶段限制行为应连到行为，不是阶段改变物品身份。若一个物品有条件效果和无条件效果，不要用物品身份作中继，把前者的条件误传播到后者；现有查询不解算条件，无法凭文字修复伪路径。

## 图与文件夹

- 文件夹回答「去哪里找」，图回答「这一张解释什么」。沿用合理分类，按**领域/内容类型 → 稳定内容族或主要机制线**分层；同层使用同一分类轴，不混放类别、具体物品和效果。不要镜像源码或按稀有度、品质、版本复制多套图；正交筛选可复用已有标签。
- 共性图解释共享资源、事件和状态转换；物品图解释具体聚合物怎样接入它们。目录不产生分类关系、继承、规则所有权或生效范围，共享概念和规则不复制。
- 分类总览回答有哪些类别，机制总览回答核心作用如何关联，不能以只列类别代替收益、代价与反馈。分类总览只保留必要类别和范围，叶级图整理具体物品，不展平全部后代。简单同族可合小图，复杂单体或独立机制线可分图；不强制一物一文件，也不按每条边碎拆。
- 每张图的 `scope` 写清本图问题与边界，不能代替已确定的影响规则。机制总览若承诺解释主干，就应选入关键连接，不依赖读者自行拼回被省略的跨系统关系。零散物品可按真实来源/类型小型收纳，注明不声明共同玩法；不为连通而造因果，未知效果允许保留孤立身份。
- `--folder` 相对 `.mechanics/mechanics`，只能使用已有目录，省略则新建到机制根。已有图不再传新建参数，不能借此搬图。只有任务确需建目录、搬图或重命名文件时才交由支持目录管理的流程处理，不绕过工具直接修改 canonical；目录还影响导航和文档分组。

## 图的颗粒度

**单张图最多包含 25 个具体规则聚合物（道具、装备、卡牌等合计），分类总览也不豁免。** 按本图焦点与所选规则端点中的具体物品身份去重；规则带入的物品也算，类别和共享资源不算。少于 25 但多主题或难以追踪时仍应拆分。先按同粒度类别/主要用途分组，确无语义差异再分册，不删除身份、合并不同物品或隐藏代价来凑数。

这是建模语义约束，不是「总节点 ≤25」。当前协议没有统一的物品类型字段，脚本不会按名称猜测具体物品数；只在创建/整理聚合物时确定这个范围，普通文字修改不重新审计全库。焦点数、所选规则数、投影节点数由 save 返回，不要求 Agent 手数或每次报告四项数量。

- 范围明确的新图优先 `ruleSelection: "explicit"`：只展示固定规则与焦点、规则端点，不继续展开邻边；加入焦点不会自动加规则。
- 省略该字段表示焦点一跳邻接规则与固定规则并集，仅在有意观察邻域时使用。共享资源可能带入更多物品；不是固定规则少就一定图小。
- **仅在拆图或切换选择模式时**，针对本次意图决定需保留的规则和上下文，不能只改模式而漏掉效果。用户指定组合视图时，按实际可见图及所选规则判断相关范围的覆盖，不能仅凭全库存在规则就声称已经展示。缩小的是本图引用范围，不是全库定义/规则，不靠折叠、缩字或排版掩盖超量。复杂批量归类可用简短分组表辅助，不默认另造报告或持久化第二份真相。

## 规则聚合物：一物一概念

每个具体道具、装备、卡牌都保留独立稳定概念、名称和定义，跨图复用。**即使没有其他引用、只有一组效果，甚至效果尚未明确，也不按冗余中间节点省略。** 普通无独立职责的单链中间量可压回规则文字，但聚合物身份是明确例外。

建模师可将它理解为「获得后这组规则才激活」的隐含条件入口；**不要求另画获得、拥有、激活节点或通用激活边**。真实的获得时触发、装备、使用、打出、命中、消耗等条件和例外仍须按作者声明或相应来源保留，不把所有物品误写成持有即无条件生效。

- 物品直接连接共享机制/资源/事件，保留收益与代价；触发、对象、限制通常写入 `ruleText`，有独立机制职责的状态/输入才建节点。不要把每个条件短语拆节点，也不要造未支持的 `condition` 字段。
- 虚构例：「守护护符」使用独立 `ward-amulet` 概念连接 `shield`，规则文字为「装备期间，每次受到伤害后获得 1 点护盾」；不补仅用于解释隐含激活的占位节点。
- 未知效果明确待确认，不按名字编造，不把建模待办写成已确定事实。缺边或未找到路径只表示当前模型未表达该关系；可能是待定、漏建或未选中，不能据此断言玩法不存在影响。

## 关系与写入边界

- 真实子类才用 `specializes`（子概念 → 唯一父概念），以“任何子实例都能无条件称为父概念”的替代检验判断；不是组成、持有、目录归属或「有某效果」，也不自动推出影响继承。需要设置父类时可用 `isa set --draft <draftId> --concept <子概念> --parent <父概念|none>`；它改当前草稿，之后直接 save。批量编辑仍可按模板修改草稿。
- 稳定组成才用 `part-of`（局部 → 整体）。它允许多整体，但禁止自连和环；不带 `sign`、`inheritance`、限定词或规则文字，不参与 impact，也不自动产生“局部影响整体”。真正影响仍另写 influence；纯阅读范围仍用元数据。
- rules v2 的规则 ID 为 `<source>-2-<target>-<relation>`，同一端点和同一关系全局唯一；influence 可与一种结构关系同端点共存，但同端点不能同时声明 is-a 与 part-of。多个影响条件和例外合入规则文字。影响规则按模板给出方向、`sign`、`inheritance`，正负不是玩家视角的好坏；`random` 用于真实随机影响，不代替尚未决定的方向。限定词只缩小 influence 端点的真实适用子集，不改变概念身份。
- definitions/rules 草稿是全库副本，不能按本图范围裁剪。`explicit` 只隔离选边范围，不隔离共享规则内容的变更。脚本自动检查候选引用，不要求 Agent 提前遍历全部消费者。
- 保存只提交 JSON；保留有效位置、清除过期路径缓存，新建图按规则维护导出选择。网页排版、视图更新、文档导出均未执行，不声称这些派生操作已经完成。
